## 外部调研候选池（2026-09-28）

按产品口径扩大调研（个人 CRM / 笔记生态 / 通讯录导入 / 思源集市与图谱 / 回顾提醒五路，详见 D-0018）后沉淀的候选方向。除已明确转入 B11–B14 和 [UI-AUDIT-02](FEEDBACK-BACKLOG.md) 的交互质量线外，其余按 `RESEARCH-FUNC-01` 功能候选与 `RESEARCH-UI-01` 交互候选分别评估；优先级表示评估顺序，未承诺进入版本。进入实现前先补契约与原型状态，不自动绑定版本号。

**功能候选（价值排序）**

1. 礼物/人情双向往来记录（WOLB「我送 Ta / Ta 送我」、Monica gifts/debts/promises）：新 JSON 契约，可进时间线、简报与报表——中文人情场景差异化最优先候选。
2. 星标收藏＋常用联系人置顶条（Google Starred / Cardhop widgets）：事实源待比较数据库字段与插件偏好索引，见 `RF-02`；若选数据库字段，需经字段健康检查机制增量补建。
3. 档案条「谈资区」：显式记录「怎么认识的 / TA 告诉过我的事 / 下次可以问的」（Obsidian 用户工作流验证），文档模板级改动。
4. 潜在关系推荐表（Obsidian Graph Analysis 共现/共同邻居）：「常被同笔记提及但尚无关系边」提示，与无关系筛选互补；已连接行淡出。
5. 周回顾文档生成（Bases CRM 周检视仪式）：一键生成超期未联系/本周生日/待办嵌入的回顾文档。
6. 「与我的关系」基础称谓已纳入 B11/B12 优先需求；FamilySearch 链式路径卡的逐边类型标签仍依赖 B05/C05 完整关系类型库建模。
7. 图谱时间轴回放（Gephi Timeline 范围滑杆 / Kumu 点击年份）：依赖新增「认识时间」字段契约。
8. 嵌套群组（WOLB）：现分组为扁平 select；组织成员归属按 B13 优先推进，分组层级仍单独评估。
9. Cardhop 式快速输入栏（「张三 138…」建档、「张三 电话」复制）：解析器成本中高，中远期。
10. 键盘度数聚焦（Kumu：±逐度/数字键跳度）、图例即过滤器（点图例项显隐分组）：图谱小增强，纯前端。
11. LvContacts v2 契约化：对齐打卡 API v5 的能力协商/防御性副本/契约自测包；消费打卡 getCalendarProjection 把生日投影进打卡日历。
12. 生日→系统日历出口（思源 CalDAV 同步插件已证明 AV→日历通道可行，远期外发通道）。

**展示与交互小项**：温度环（按个人节奏换算的可解释温度，挂 F06）；卡片大字显示号码（分享场景）；日历格密度圆点；空态「三件套」已入质量线（PRODUCT-PLAN §4）。

## 已知问题（待真实宿主验证，2026-09-28）

- **插件 i18n 资源文件名可能不被宿主加载**：本仓库用 `i18n/zh-CN.json`、`i18n/en.json`，
  而内核二进制里可检索到 `i18n/zh_CN.json` 与语言代码表（`en_US`/`zh_CN`），思源自身插件
  （如 siyuan-checkin）用 `zh_CN.json`/`en_US.json`。若宿主按语言代码取文件，本插件的
  `this.i18n` 会为空，界面实际显示组件内中文回退——中文用户无感，英文用户看不到英文。
  未在真实宿主验证（按作者要求跳过），故不改名；待真机确认后一次性调整（含
  check-release 清单、parity 测试路径与 ui-smoke 的英文导入）。
- 初始化向导的续建识别只认「联系人总表」文档标题：若用户改过宿主文档标题，向导会新建
  一份而不是复用旧文档。放弃按文档名反查锚点（D-0006）后的取舍，留观是否需要在
  预检提示里列出候选。

## 从笔记捕获人脉（2026-09-27 落地 v0.2a + 演进设计）

**场景**：一篇会议/聚会笔记里提到多人——已入库的记"共同交集"，未入库的引导收编。

**v0.2a 已实现（确定性，零 AI 依赖）**
- 识别：笔记内的块引/双链（`((文档ID "名字"))` / siyuan://blocks 链接）经 refs 索引 100% 确定
  → 与名册交集 = 已入库参与者（E2E 实证 refs 索引覆盖 kramdown 块引）
- 确认 UI：「从笔记捕获」弹窗（命令面板"captureFromNote"或编辑器右键"人脉：捕获本文人员"）：
  勾选参与者 + 新人名单（按名收编）+ 日期/地点/备注
- 记录：每人一条互动事件（source=diary，**externalRef=笔记 ID 即"同场身份"**，幂等防重复捕获）；
  日期/地点/备注随事件保存
- 体现：①人物文档档案条与"久未联系"自动更新 ②笔记末尾写入「参与人员」双链区块
  （原生反链可见，会议文档 ↔ 人物文档互相指回）③同场人员共享 externalRef →
  后续可做"共同出席 N 次"统计与图谱"同场"虚线边
- 设计决策：共同出席**不自动建** related 关系边（同场 ≠ 有关系），只记同场事实（D-0011）

**v0.2b AI 抽取已实现（可选增强，需思源内置 AI 配置）**
- 在确认 UI 增加"AI 分析本页"：抽取出**未链接的纯文本人名**、时间、地点、新人员建议
- 人名候选与名册做精确匹配预填；一切结果进确认 UI，用户勾选才落库——AI 只做提名不做决定
- 隐私边界：笔记内容仅在用户点击分析时发送到用户自己配置的思源 AI 端点；插件不持有密钥、无后台扫描

**v0.2c 跨插件协作已实现：人脉插件作为"人员服务"提供方（D-0012）**
- 协议：`window.LvContacts = { protocol: 1, capabilities: [...], searchPeople(keyword),
  ensurePerson(name) → docId, recordInteraction(docIds, {ref, date, place, note}) }`
  ——与打卡的 window.siyuanCheckin 协议 v5 同款形态，带版本协商与能力声明
- 用法：任务管理类插件在任务表单加"参与人员"选择器（调 searchPeople 搜索 / ensurePerson 新建），
  任务完成/到期时调 recordInteraction 记录共同交集——一场会议待办、一次家庭聚会即一次同场事件
- 推进路径：①本插件协议与文档已完成 ②外部插件接入需另行协调
  ③同时经 `addAgentCapability` 注册 Agent 能力（"查人/建人/记交集"），任何支持思源 Agent 的
  插件与流程都能间接调用——官方通道一次接入处处可用
- 原则：不逆向、不监听其他插件的私有存储（D-255 纪律）；集成只走公开桥或官方 Agent 通道

## 需求③ 关系的显示与延伸（深化设计）

现状：related relation 字段（双向，内核自动回链）+ cytoscape 图谱（分组着色、度数定大小）+ 详情弹窗增删。

**显示层演进**
1. 人物文档「相关人物」链接区块已实现；其 Markdown 链接是否在思源原生图形成预期引用边仍需 B14.2 实证。关系类型标注尚未实现，依赖后续建模。
2. 图谱交互：边按关系类型过滤；点击节点高亮一度邻接、二度展开（"朋友的朋友"）；
   两点最短路径（"A 怎么认识 B"，引荐链查询）；按认识时间的时间轴回放。
   已落地：选取关系中心高亮直接或严格二度邻接，选择对比人物查看共同联系人或最短连接路径；查询限于当前展示图，点击节点仍打开详情。关系类型过滤仍未实现。
   最短路径复用 Cytoscape 无权无向 Dijkstra，等长链路只展示一条，不表示引荐意愿或关系强弱；筛选/裁剪可能移除中间人物，无路径仅指当前图内无连接。
3. 结构洞察：共同联系人高亮；"桥梁节点"识别（连接两个社群的人，弱关系价值，Granovetter）；
   孤立节点提醒（0 关系的人，引导补全）。
   已落地：无关系人物筛选，按完整名册的有效显式关系判断，自环与悬空关系不计；不是根据搜索后的图判断，也不是自动提醒。

**建模层演进（组织优先，完整关系库后续；见 D-0005 / D-0021）**
- 独立"关系库"：一行 = 一条关系（甲 / 乙 / 类型 / 强度 / 开始时间 / 备注）。
  类型自定义（家人/同事/上下级/引荐人/师生…），支持非对称（父母→子女）；
  图谱边从关系库读取后可着色/过滤；从现有 related 字段一键升级（同边迁移，类型留空待补）。

## 新反馈：CardDAV 通讯录与 CalDAV 日历同步（2026-10-06，候选待办）

用户希望把人脉与手机通讯录、待办提醒打通。该方向有价值，但必须拆成两个独立协议和两个可回滚的同步域：CardDAV 只同步联系人卡片，CalDAV 只同步跟进/重要日期；不能把整个人脉库或互动历史直接外发。

### CARDAV-01：CardDAV 能力调研与契约 spike（P2 / candidate）

- 先验证 RFC 6352/ vCard 3.0、4.0 的发现流程：`/.well-known/carddav`、principal、addressbook-home-set、addressbook collection、`REPORT addressbook-query/addressbook-multiget`、ETag/`If-Match`、`sync-token` 和分页。
- 用受控测试账号验证 Nextcloud、Radicale、iCloud（或明确排除的服务）以及思源前端 CSP/CORS、Basic/OAuth/应用密码、TLS 失败和代理环境；不能直接假设所有 CardDAV 服务兼容同一 URL 或鉴权。
- API 契约只允许 `src/api/carddav.ts` 出网，服务层编排，域层做 vCard 映射；凭据不写普通插件 JSON、不进日志、不进迁移包，优先使用宿主可用的凭据存储，若无安全存储则只支持每次会话输入。
- 产出字段矩阵和服务器兼容矩阵后才能开实现卡；spike 失败时保留 vCard 文件导入导出，不做半成品在线同步。

### CARDAV-02：联系人同步字段与安全策略（P2 / ready after spike）

允许同步的最小字段：姓名、多个电话、多个邮箱、网站、生日（公历）、公开备注、标签/分组（服务支持时映射到 CATEGORIES）。默认不同步：思源 docId/itemId、related 关系、组织成员与任职历史、互动时间线/地点/备注、跟进、本人标记、AI 内容、私密扩展字段、原文链接中的块 ID。头像、农历生日、自定义字段和多值顺序需逐项显示兼容性，不静默丢弃。

MVP 先做“手动预览 → 单向导出/导入”；双向同步再增加每条记录的远端 UID、ETag、上次同步快照和本地修改时间。冲突按字段报告 local/remote/both，默认暂停该条等待选择；远端删除进入回收/待确认列表，绝不因一次同步删除思源人物文档。新增、更新、删除均需逐条结果、重试和未知状态，不能用姓名合并同人。

### CARDAV-03：CardDAV 双向同步 UI 与运行策略（P2 / blocked by CARDAV-01/02）

设置页增加“通讯录同步”向导：服务器地址/地址簿选择、鉴权测试、字段开关、隐私预览、首次同步方向、冲突策略、手动同步/暂停/断开和导出诊断。首页显示上次成功同步、待处理冲突、失败条数；不做后台常驻和静默定时任务，首版仅用户点击或工作台打开时同步。同步前后均可导出脱敏报告，绝不展示密码/token。

验收覆盖新建/更新/远端删除/本地删除、同名不同人、ETag 冲突、分页/断点、服务器离线、401/403、证书错误、重复点击、半成功和未知写入；本地人物文档和关系图在任何失败下保持不变。真实手机通讯录可见性作为宿主/设备验收，不用隔离 mock 代替。

### CALDAV-01：CalDAV 发现与日历/提醒契约 spike（P2 / candidate）

验证 RFC 4791 的 principal、calendar-home-set、calendar-query/multiget、ETag/`sync-token`、VEVENT/VTODO、STATUS、DUE/DTSTART、重复规则和 VALARM；确认 Nextcloud/Radicale/iCloud 对 VTODO 与提醒的实际支持差异。先决定“跟进事项用 VTODO”还是“日历事件用 VEVENT”，不把支持某一服务误称为 CalDAV 全兼容。

### CALDAV-02：跟进事项到手机提醒（P2 / blocked by CALDAV-01）

建议 MVP 只同步插件已有 follow-up：标题、到期日、状态、人物显示名（可配置是否带姓名）、UID、更新时间和可选提醒时间；完成/取消双向回写需显式开关。生日/纪念日作为独立 VEVENT 年度事件候选，互动历史、关系、私密备注和人物全文默认不同步。VALARM 是可选能力，服务不支持时要明确提示“已写入日历但未保证系统通知”。

设置页提供目标日历、同步范围、提醒提前量、双向开关、仅手动/打开工作台触发、失败重试与冲突队列；删除遵循“远端回收/确认”，不能因删除插件任务而直接删除用户已有日历事件。验收包含手机锁屏通知、离线恢复、时区/DST、全天事件、重复点击、VTODO 不支持时的降级提示和跨服务 UID 稳定性。

### 先后顺序与明确边界

1. 先完成恢复态、备份和真实宿主验收，再做协议 spike；同步不能掩盖本地数据可信问题。
2. CARDAV-01 与 CALDAV-01 只读调研和受控测试，不写主流程、不采集真实用户通讯录。
3. 通过契约后先做 CardDAV 手动单向预览/导出，再做双向；CalDAV 先做 follow-up → VTODO，再评估生日 VEVENT。
4. 两条同步都必须有“同步哪些/不哪些”清单、每条冲突解释、可暂停/断开、脱敏日志、凭据清除和完整回滚说明；不承诺后台常驻通知或所有手机厂商一致行为。
