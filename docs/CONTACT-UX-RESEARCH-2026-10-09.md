# 联系人与人脉功能对标研究（2026-10-09）

本次调研围绕两个问题：通讯录事实如何保持清晰，以及“人脉”如何帮助用户持续维护关系。结论是，CardDAV 只应负责联系人标准字段；互动、关系、组织、跟进、联系节奏和隐私备注仍由插件本地管理。

## 对标结果

| 软件/协议 | 值得参考的设计 | 融入当前插件的方式 | 不直接照搬的部分 |
| --- | --- | --- | --- |
| Nextcloud Contacts | 多地址簿、地址簿共享、只读集合、服务器权限 | 同步账户下逐个选择地址簿；记录只读能力；只读地址簿隐藏上传/删除 | 不把多个地址簿自动合并成一张本地通讯录 |
| DAVx⁵ | 账户→地址簿分层、单独启用/禁用、手动刷新、强制重新同步、详细诊断 | 设置页显示账户、地址簿、上次同步、失败、冲突和待确认删除；提供“重新扫描地址簿” | 不把 Android 后台同步行为当作思源插件已有能力 |
| Google CardDAV | HTTPS、OAuth、动态发现、vCard 3.0、CTag/sync-token，服务能力并不完整 | 先做能力探测；认证方式按服务器声明；不硬编码地址簿 URL | 不以“支持 Google”推导为“兼容所有 CardDAV” |
| Apple iCloud 联系人 | 多联系人 vCard 导入/导出；联系人列表和 vCard 文件边界清楚 | 保留现有文件导入导出；导入前展示卡片数量、支持字段和忽略字段 | 不把 iCloud 网页导入导出当作 CardDAV API 兼容证明 |
| Radicale | 轻量地址簿资源、vCard 文件对象和同步令牌 | 作为首个标准 CardDAV 兼容测试目标之一 | 不省略 ETag、权限和资源 URL，仅因服务简单就按姓名同步 |
| Monica | 联系人、备注、活动、关系、提醒、任务、重要日期拆成独立对象 | 继续分离互动、个人备注、关系称谓、跟进、提醒和组织成员；人物概览提供关系摘要 | 不把所有对象都塞入 CardDAV 或人物长文本 |
| Dex | 记录如何认识、工作/教育背景、家庭、重要日期和联系上下文 | 在人物概览中显示最近互动、待办跟进、联系节奏、相关人数量；补充关系上下文字段时保持本地 | 不把 AI 生成的上下文当成已确认事实 |
| Cloze | 自动、周期、计划三类提醒；有互动后自动顺延，避免重复提醒 | 联系节奏与互动日期联动；已完成互动后重新计算久未联系；首页统一展示行动 | 不在没有明确互动证据时自动修改用户手动跟进 |
| Clay/Mesh | Review/Home 工作流、群组联系节奏、重新联系建议 | 强化首页行动分组、群组/组织维护节奏和“联系前回顾” | 不新增静默后台采集邮件、社交网络或消息内容 |

## 当前功能的直接改进

### 1. vCard 页面先讲清边界

导入导出弹窗现在在操作区前展示四块说明：当前支持字段、不会写入的内部资料、单值字段的多值限制、CardDAV 尚未接入。这样用户在选择文件前即可知道：组织、关系、互动、跟进、提醒、本人、AI 和思源 ID 不会混入通讯录文件。

预览仍保留逐卡映射、已忽略属性和需人工核对状态。下一步若扩展多值电话/邮箱，应把“每个值及类型”作为独立映射展示，不能继续把 `138 / 021` 当作一个可拨号号码。

### 2. 人物概览增加关系摘要

人物详情概览现在增加“关系摘要”，集中显示：

- 最近互动日期；
- 未完成跟进数量；
- 当前联系节奏（跟随全局、自定义天数、已暂停）；
- 已建立的相关人数量。

摘要只做状态投影，不复制或改写互动、跟进和联系节奏事实；用户可以直接进入互动页继续记录。这个模式对应 Monica/Dex 的上下文档案和 Cloze 的维护提醒，同时适配当前已有服务，不新增外部数据采集。

### 3. 首页与详情保持同一套维护口径

当前已经有生日、久未联系、跟进和联系节奏模块。后续 UI 优化应统一以下文案和动作：

- “完成跟进”表示计划完成，不等同于“已发生互动”；
- “记录互动”才更新最近联系日期；
- “暂停联系节奏”只暂停提醒，不删除历史互动；
- “稍后处理”应保留原事项并展示新的日期；
- 读取失败、无数据、未配置三种状态必须分别显示，不能用空列表代替读取失败。

### 4. 组织和 CardDAV 保持隔离

组织资料、部门、任职期间、归档状态、共同背景和人物—组织双链属于插件内部关系事实。即使 CardDAV 后续支持 `ORG`、`TITLE`，也不能把多组织、多段任职历史压成一条远端字段。可以在未来提供“明确选择某一当前组织后同步公司/职位”的可选映射，但必须显示这是快照，不是完整任职历史。

## 建议的联系人数据模型演进

当前模型有单个电话、邮箱、网站；同类软件和 vCard 标准都支持多值及类型。按风险分阶段：

1. 先在本地模型增加结构化值与类型，例如 `phones: [{value, type}]`、`emails: [{value, type}]`、`websites: [{value, type}]`；旧单值字段作为兼容投影。
2. vCard 文件导入预览显示每个值，用户可选择主值、追加值或跳过；导出保留所有值和类型。
3. CardDAV 只在结构化模型完成后开启多值双向同步；在此之前明确“只同步主值”并显示损失提示。
4. 地址、公司、职位、头像、纪念日、自定义字段按独立字段加入，不能通过 NOTE 或 X-* 偷塞。

## 同步设置的产品结构

参考 Nextcloud 和 DAVx⁵，建议分成四层：

1. **账户**：服务器、认证方式、凭据状态、连接测试、删除账户。
2. **地址簿**：名称、URL、读写权限、vCard 版本、启用/禁用。
3. **范围**：本地联系人筛选、同步字段、首次同步方向（仅下载/仅上传/双向）。
4. **状态**：上次成功时间、本地变化、远端变化、冲突、待确认删除、失败和重试。

每次同步前显示“将同步/不会同步”两张清单；同步后提供逐条结果和脱敏诊断。账户删除只清除远端绑定和凭据引用，保留本地联系人；远端删除进入待确认区，不自动删除人物文档。

## 优先级

### 可以立即做

- 现有 vCard 页面边界说明（已完成）。
- 人物概览关系摘要（已完成）。
- 将“记录互动”“完成跟进”“暂停节奏”的区别统一到首页与详情文案。
- 在设置中增加“当前同步仍未支持 CardDAV”的明确状态入口，避免用户把 vCard 导出按钮理解为在线同步。

### CardDAV 之前必须做

- 多电话、多邮箱、多网站的本地结构化模型。
- vCard UID、原始未知属性和参数保留层。
- 服务器能力探测、地址簿权限和认证方式模型。
- 远端 UID/href/ETag、上次快照、sync-token 和冲突状态。

### CardDAV 稳定后再做

- 联系前回顾卡片；
- 群组级联系节奏；
- 公开备注和头像的可选同步；
- Google OAuth、iCloud 等服务商适配；
- 用户主动开启的定时同步。
