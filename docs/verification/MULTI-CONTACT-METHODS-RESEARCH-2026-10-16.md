# 多联系方式与自定义条目研究（2026-10-16）

本研究对应 Issue #51/#54，范围是候选契约、兼容边界和搜索成本。它没有接入生产存储、AV 写入、迁移包、vCard 服务、桥或 UI，也不表示任何候选结构已经采纳。

2026-10-17 复评边界：本文及 28 项旧检查是第一轮历史研究。旧 `snapshotPreview` 尚未严格校验墓碑、revision 和所有未知字段；`backupMergePreview` 使用双方墓碑过滤条目后，没有把无冲突的外来墓碑写回输出，连续恢复可能复活条目。两个分别合法的输入合并后也可能产生双主值，旧检查未覆盖。因此不能把旧“严格快照/墓碑优先”措辞解释为完整严格恢复已通过。后续反例和候选修正放在独立 [S2 实验](MULTI-CONTACT-RECOVERY-2026-10-17.md)，保留旧脚本和原结果作为历史对照。

脚本在三个独立 Node 子进程中运行扫描、索引和迁移测量。所有姓名、联系方式和 ID 都是虚构值；内核调用数为 0。

## 当前边界

现有联系人模型的电话、邮箱、微信和网站是 AV 单值列。当前 vCard 解析器对多值输入的行为是：多个 `TEL` 去重后拼接到一个 `phone` 字符串，多个 `EMAIL` 和 `URL` 各取首项；序列化也各输出一个电话、邮箱和网站。这是当前兼容行为，不是多联系方式事实源。

当前 AV 搜索只知道 AV 主值。如果其他联系方式只放在插件列表中，继续把关键词下推到 AV 会漏掉次要值。因此“能保存多个值”和“能搜索所有值”必须作为同一个研究问题处理。

## 事实源方案比较

| 方案 | 优点 | 主要风险 | 研究判断 |
| --- | --- | --- | --- |
| AV 持有全部联系方式 | 原生表格可直接编辑、AV 搜索自然覆盖 | 每种类型的数量、标签、顺序和删除墓碑需要额外列或复杂编码；旧列和第三方编辑难以保留稳定条目身份；vCard 多值仍需编码 | 不能仅凭现有 AV 单值列扩展；需要新的隔离 spike 验证列/类型能力后再考虑 |
| 列表持有全部值，AV 仅投影主值 | 可表达稳定 ID、类型、标签、顺序、主值、删除墓碑；复杂字段不污染主库 | 原生 AV 编辑主值会与列表发生冲突；列表写成功而投影失败会形成跨存储未知状态；搜索需要插件索引或有界扫描；删除插件数据可能丢失次要值 | 初轮研究候选，尚未采纳；2026-10-17 增补原生文档全量备选，见下文 |
| 仅把多值拼到现有单值列 | 改动最小 | 丢失值边界、标签、顺序和身份，无法安全编辑/删除/恢复；搜索与导出语义不稳定 | 明确排除 |

若继续研究“列表 + 主值投影”，候选记录可暂记为 `contactMethods`，字段身份、事实源和版本仍需正式契约评审。研究夹具使用了 `id/type/value/label/isPrimary/order`，不应直接复制到生产类型。

更新后的 D1 另比较“人物原生文档保存全部方法、AV 只投影主值”：它可以保留删除插件数据后的原生可读事实，但新格式、手工编辑、扫描和投影恢复仍需实验。本轮不采纳 JSON 为唯一全量事实源，详见 [数据主权比较](MULTI-CONTACT-OWNERSHIP-2026-10-17.md)。

## 原生编辑、投影和失败恢复

跨 AV 与插件列表没有原子事务。每个写入都必须在同一稳定 `personDocId`、唯一 AV `itemId`、数据库锚点和请求 ID 上核实。

| 观测 | 研究结果 | 后续要求 |
| --- | --- | --- |
| 写入请求响应丢失，但回读值等于期望 | 可标记为 `verified`，不重放 | 以回读为准，保留原请求键 |
| 请求未知，回读仍是旧值 | 只能标记 `unknown` | 不自动重试或覆盖；由用户显式核实/重试 |
| 回读发现 AV 值已被其他入口改动 | 标记 `native_edit_conflict` | 显示旧列表、AV 当前值和选择动作 |
| 目标行、人物文档或锚点变化 | 标记 `target_conflict` | 停止投影，不按姓名重新绑定 |
| 列表事实已保存，AV 投影失败 | 事实仍保留，投影待修复 | 逐步骤报告和显式重试，不报告整体成功 |

研究脚本对这些状态做了纯函数模拟，未声称验证真实宿主的跨端点并发。

## 旧值迁移与身份

旧电话中的 `" / "` 可能是当前 vCard 导入器的历史拼接，也可能是用户手工输入的原文。迁移预览将整段旧值保留为一条 `legacy-av` 值，并标记“可能需要拆分”；不能自动按分隔符创建多个号码。

条目 ID 必须由原人物稳定身份和旧字段槽位派生，不能由姓名、值或数组位置临时生成。研究夹具验证了：改名、改值、改标签和重排不改变方法 ID；同一值属于不同人物时也不会共享身份。新文件的同名或同值只进入预览和人工消歧；只有同一已确认请求重试可以沿用原身份。

未知版本、未知类型、重复 ID、同类型多个主值和非法空值均在预览阶段拒绝，且不修改输入快照。备份合并以当前值优先，墓碑优先于旧备份，已删除条目不能被旧备份复活；同 ID 不同内容形成冲突项。

## vCard 研究边界

脱敏夹具包含两个 `TEL`、两个 `EMAIL` 和两个 `URL`。当前生产纯解析器实际得到：电话为 `+00 111 / +00 222`，邮箱为第一项，网站为第一项。该结果确认了 Issue #51/#54 的多值缺口，但没有实现候选多值 vCard 映射。

正式实现前仍需决定：

- 每个 `TEL`/`EMAIL`/`URL` 如何保留类型参数和用户标签；
- 没有标准属性的微信、QQ、custom 值是否导出，导出时如何逐项提示损失；
- 导入重复值如何进入预览，不能凭姓名或值静默覆盖现有条目；
- 多值往返、未知属性和旧单值导出如何在备份/恢复中保持可解释。

## 搜索成本 spike

夹具生成 10,000 个人、每人 10 条联系方式，共 100,000 条值。匹配规则为 NFKC + 小写 + 字面子串，结果按稳定人物身份去重。

| 策略 | 构建 p95 | 选择性查询 p95 | 最坏查询 p95 | 索引保留堆增长 | 结果 |
| --- | ---: | ---: | ---: | ---: | --- |
| 每次规范化有界全扫描 | 34.88 ms | 1.25–5.52 ms | 5.52 ms | 约 9.3 MiB | 选择性与宽匹配都正确；需要完整扫描才能声称 complete |
| 可重建 trigram 索引 | 416.97 ms | 0.01–0.13 ms | 2.89 ms（短词回退全扫描） | 约 26.36 MiB | 选择性查询减少访问；短词和宽匹配仍需扫描/大量候选核验 |
| 严格快照预览 | 20.84 ms | — | — | 约 10 MiB 保留增长 | 100,000 条值的结构校验通过 |
| 旧 AV 迁移预览 | 35.88 ms | — | — | 约 11.7 MiB 保留增长 | 10,000 个人、40,000 个旧字段值通过；电话分隔符未自动拆分 |

上述是 Windows x64、Node v24.16.0、Intel i5-14600KF、纯内存数据的单机测量。脚本将以下阈值写入结果文件作为**临时研究预算**：索引构建 p95 ≤ 2 秒、全扫描查询 p95 ≤ 250 ms、选择性索引查询 p95 ≤ 50 ms、索引保留堆增长 ≤ 128 MiB、快照/迁移预览 p95 ≤ 1 秒。7/7 项在本次合成数据上通过，但 `acceptedForProduction` 明确为 `false`。

对搜索的候选解释是：

1. 选择性长词可使用可重建索引；索引是派生数据，不是联系方式事实源。
2. 短词、宽匹配、索引缺失、索引版本未知或取消时，只能使用分块扫描；未扫完整必须显示 `partial/unknown`，不能显示为空结果。
3. 与现有 AV query 的整合、缓存失效、跨窗口刷新、宿主大库耗时和实际 JSON 读写尚未测量。

## 两层自定义条目（后置）

联系方式方案通过前，不研究通用条目树。后续若仍有需求，只评估最多两层的独立结构：子项只能指向同一联系人内的顶层父项；拒绝循环、悬空父项和无限递归；排序使用稳定 ID 与显式顺序；删除父项先预览子项影响，不级联删除子项。

联系人方法、组织经历、互动、跟进和人物备注的事实源、生命周期、隐私和恢复边界不同，不应首版合并为一个树，也不应把现有组织部门的层级校验直接当作联系人条目契约。

## 研究结论与未决项

本轮 28 个纯域检查全部通过：次要电话/邮箱/微信/网址可被扫描和索引找到，扫描与索引结果一致；取消和未完成扫描不会伪装为空成功；稳定身份、旧分隔符原文、未知版本/类型、墓碑优先和投影冲突均有可复现检查。

结论仍是**候选**：列表事实源 + AV 主值投影 + 可重建搜索索引值得进入下一张正式契约卡，但尚未决定采用，也没有生产 schema、API 或 UI 变更。正式实现前必须补：真实 AV/宿主能力 spike、跨窗口竞争、JSON 备份文件读写、完整 vCard 多值往返、投影修复队列、隐私确认和真实规模预算。任何一项未通过，都应延期或缩小范围。
