# 组织成员列表优化：官方参考与本轮决策

日期：2026-10-18（Asia/Shanghai）。范围：组织管理中的成员浏览与操作。本文记录本轮公开官方文档核实和已选 UI 方案；实现回执、截图及实测结果由主任务随后补充。本文件不预先声明测试通过，也不代表日常用户库、原生编辑器、多窗口或手机真机验收完成。

## 1. 问题与目标

组织成员增多后，连续展开的成员列表和每行并列的多个操作会增加查找与误操作成本；添加成员表单常驻还会压缩已有成员的浏览空间。本轮目标是保留现有搜索、状态筛选和成员经历契约，以有界分页、清晰计数和稳定行操作改善大列表管理。

`active` / `former` 表示当前归属与历史经历，不是协作软件的账号权限。一个人物可以有多段历史经历；成员记录数不能未经去重就称为联系人总人数。“移除这段成员历史”也不等同于删除联系人或组织文档。

## 2. 已核实的官方模式

以下页面均在本轮通过公开 HTTP 读取核实。仅将页面明确记载的交互作为事实；没有登录这些产品执行管理操作。

| 官方来源 | 页面可核实的模式 | 对本插件的启发与边界 |
| --- | --- | --- |
| [Slack：Browse people and user groups in Slack](https://slack.com/help/articles/360003534892-Browse-people-and-user-groups-in-Slack) | `Directories → People` 中可按姓名、职位、团队、邮箱搜索；`Filters` 缩小结果，`Account type` 可区分访客、停用账号或所有者/管理员；点击头像打开人物档案。 | 保留统一搜索与独立状态筛选；常用查看入口清晰可达。账号权限与停用状态不能直接套用为插件的当前/历史经历。该页没有规定分页或每页条数。 |
| [Microsoft Teams：Remove someone from a team](https://support.microsoft.com/en-us/teams/teams-channels/remove-someone-from-a-team-in-microsoft-teams) | `Manage team → Members` 可按姓名搜索；桌面端在成员行最右侧移除；移动端通过成员姓名或更多菜单进入移除。官方明确区分移出团队与移出整个组织的权限和范围。 | 固定行操作位置，窄屏收起次要操作；继续明确移除的范围和影响，复用现有确认流程。该页没有记载排序或分页规则。 |
| [Notion：Manage members, admins & guests](https://www.notion.com/help/add-members-admins-guests-and-groups) | 设置中以 `Members` / `Guests` 区分列表；成员角色通过行内下拉更改；临时成员行的 `•••` 提供有效期编辑与移除；访客批量升级先勾选，再执行带所选数量的 `Upgrade {#} guest(s) to member`。 | 将状态筛选、常用行操作与次要操作分层；需要批量能力时先明确选择数量。本轮不引入账号权限、邀请流程或新的批量破坏性写入。该页未证明成员列表搜索或分页方式。 |

本轮采用默认 20 条、可选 50/100 条的分页，是本插件针对弹窗空间、DOM 数量与回归边界的工程选择；不归因为 Slack、Teams 或 Notion 的官方默认设置。

## 3. 本轮已选方案

| 项目 | 决策与验收语义 |
| --- | --- |
| 搜索与状态筛选 | 沿用现有成员搜索和 `all` / `active` / `former` 筛选语义，不新增独立事实源。搜索、状态或组织变化后，从相应结果的第一页读取；空结果明确表示“当前筛选没有匹配成员”。 |
| 当前/历史计数 | 同时展示当前成员与历史成员的数量，区分组织总览计数与当前筛选匹配数。按成员记录/经历统计的数字须明确口径，不把同一人的多段历史当作多个不同联系人。分页切换不能改变组织总览计数。 |
| 有界 UI 分页 | 默认每页 20 条，可选 50/100 条；显示当前范围、匹配总数及翻页入口。下一页存在与否以 `total` / `hasMore` 和实际返回结果核实，不将未加载内容当作空数据。删除或筛选导致末页失效时，落回最后有效页或第一页。 |
| 常用与次要行操作 | “查看详情”和“编辑”作为两项常用操作；“移动”“接替”“移除”等进入成员行的更多菜单，继续遵循原能力与状态条件。所有操作按稳定成员记录 ID 作用于准确经历，同名人物与同人多段经历不能串行。 |
| 添加成员区域 | 已有成员时默认收起添加表单，提供明确的“添加成员”展开入口，把空间让给浏览。已有但无成员的空组织仍可展开添加，不要求重新创建组织；不能把“筛选无匹配”误认为组织真的没有成员。 |
| 草稿守卫 | 分页、每页条数、筛选、组织切换、关闭和其它成员操作继续遵守现有草稿守卫。保存、取消或确认放弃之前，不通过刷新、折叠添加区域或翻页静默丢弃输入。 |
| 位置与焦点 | 成员保存后的重读尽量保留当前页、搜索、状态筛选和浏览位置。关闭更多菜单或完成/取消操作后，焦点返回合理的原入口；记录被移除或过滤掉时回到相邻记录或成员工具栏。恢复位置时仍须核对当前组织与请求归属。 |
| 失败与重试 | 初次读取、翻页与写后重读分别保留加载/错误反馈；失败不伪装为空列表，不能因旧请求后返回而覆盖新组织或新筛选结果。 |

## 4. 服务与数据契约边界

现有 `ContactsFacade.listOrganizationMembersPage(orgDocId, { query, status, offset, limit })` 已提供分页入口；`OrganizationMemberPage` 返回 `items`、`offset`、`limit`、`total`、`hasMore` 以及用于成员身份排除的完整人物 ID 集合。生产实现位于 `src/services/org.ts`，域层 `pageOrgMemberships` 已支持稳定分页及 `limit` 校验。

因此本轮不需要新增服务端点、变更成员记录结构或改变 `active` / `former` 的数据契约。20/50/100 均在现有限制内。组件仍通过 facade 读取；“有界 UI 分页”只约束每页显示和读取窗口，不意味着底层组织扫描已改为数据库级分页，也不能据此宣称万级真实库性能已验收。

已有成员编辑、移动、接替、移除、归档组织和历史补录的写入保护与回执继续适用。归档组织中编辑职位/备注时须保留原状态，不能由列表重排或表单重置隐式结束当前经历。

## 5. 人工验收清单

以下为待执行或待主任务回填的清单；复选框不表示已经通过。

- [ ] 既有空组织、有当前成员组织、仅有历史成员组织、归档组织、已移除组织分别可打开，状态和可用操作准确。
- [ ] 姓名、部门、职位等现有搜索路径与当前/历史筛选继续有效；空筛选结果不会自动认定为空组织。
- [ ] 当前/历史计数与组织完整记录一致；同名人物和同人多段历史保持稳定身份及准确口径。
- [ ] 使用 0、1、20、21、50、51、100、101 条及更多成员，核对默认 20 条、50/100 选择、首末页、总数、范围和翻页按钮状态。
- [ ] 在后续页搜索或改变状态筛选，回到对应结果第一页；改变页大小后不会产生越界空页或跳过成员。
- [ ] 在后续页编辑保存，筛选、页码、合理浏览位置及焦点保留；删除末页最后一条后退回有效页。
- [ ] 每行只突出查看详情与编辑；更多菜单的移动/接替/移除可用条件与原实现一致，移除仍说明只影响该段成员历史并要求确认。
- [ ] 有成员时添加表单默认收起；展开、折叠、添加成功和失败重试行为清晰；旧空组织仍可进入添加流程。
- [ ] 添加、编辑、移动、接替或移除确认存在草稿时，翻页、筛选、改页大小、切换组织和关闭均不会静默丢稿。
- [ ] 读取慢、翻页失败、组织已不可达、外部变更及快速切换请求时，界面保留正确错误/重试信息，不显示假空态、不混入旧组织结果。
- [ ] 键盘可顺序到达搜索、筛选、分页、查看、编辑及更多菜单；菜单可用 Escape 关闭，焦点可见且返回位置合理。
- [ ] 桌面与窄视口中长姓名、长部门/职位、多行备注、日期、计数和操作按钮不遮挡、不挤压成逐字换行；明暗宿主样式保持可读。
